## 1. Flujo completo y causa raíz

`src/views/WhatsAppView.vue` abre un chat con `selectConversation`, que invoca `whatsappStore.fetchMessages(id)`. Al perder SignalR, su fallback cada 15 segundos vuelve a solicitar los mensajes del chat activo. La recepción en vivo llama a `handleRealtimeMessage` → `whatsappStore.applyRealtimeMessage` → `upsertMessage`, incorporando contenido, imágenes y estado sin nuevo HTTP.

**Defectos comprobados por inspección de main:**
1. `src/store/whatsapp.ts` iniciaba un `whatsappApi.getMessages` nuevo en cada llamada, aun con otra del mismo chat en vuelo. No existía deduplicación ni cancelación para el historial.
2. Al resolver el GET, hacía `messages.value[id] = sortMessages(res.data ?? [])`: un snapshot viejo podía **borrar un mensaje/medio recibido por SignalR** o sustituir una actualización de estado más reciente.
3. Al cambiar de sesión, `clear()` borraba el array pero no invalidaba la respuesta GET pendiente; una respuesta vieja podía repoblar el store. `resetConversationForTesting` sufría la misma carrera.
4. `isLoadingMessages` era un solo booleano; al acabar una petición para A lo ponía en falso aunque otra petición para B siguiera en vuelo.
5. Al terminar una respuesta anterior, el store podía restar el unread local mientras ya se había recibido un evento nuevo no leído.

**API/SQL:** `src/services/MainAPI/whatsappApi.ts` llama `GET /api/whatsapp/conversations/{id}/messages`. `WhatsAppController.GetMessages` está protegido con `[Authorize(Roles = "Superadmin, Admin, Cashier")]`; obtiene la conversación, comprueba `CanAccessConversationAsync` y canales/sucursal, marca como leído cuando procede, y luego consulta `WhatsAppMessages` en EF Core ordenando por `Timestamp, Id`. **Aquí no hay handler MediatR**: el controller usa `IApplicationDbContext` directamente. Los filtros multi-tenant existentes no se modifican.

**Medios/N+1 y caché:** `EnsureMediaDownloadUrlsAsync` recorre los mensajes con URL y llama secuencialmente a la capa de almacenamiento para asegurar su descarga. Es un trabajo potencial por archivo, distinto de N+1 SQL; el número/costo real no está medido. El método GET no tiene paginación: devuelve todo el historial. En `WhatsAppMessageConfiguration.cs` constan índices separados por `ConversationId` y `Timestamp`, pero no se ejecutó EXPLAIN ni se propone índice compuesto sin evidencia de cardinalidad. No se añade caché permanente de mensajes: los refrescos separados siguen pudiendo consultar contenido reciente. Mensajes de Flutter, Next.js y Print Agent no utilizan este flujo visual y sus repos no requieren cambios. No se modifican workers, SignalR, la automatización de IA ni facturación.

## 3. Corrección implementada

**Único repositorio de código:** `savelasquezs/senorArrozFront`, en nueva rama desde main.

- `src/store/whatsapp.ts`: mapa de solicitudes pendientes por `conversationId`, compartiendo la promesa mientras está viva; tras finalizar se permite el siguiente refresco. Se mantiene un contador/revisión para detectar actualizaciones SignalR durante la consulta y conservarlas al incorporar el snapshot HTTP. La respuesta ya no marca como leído un mensaje que se haya recibido después de iniciar el GET.
- `clear()` y `resetConversationForTesting` invalidan las peticiones en curso y las abortan. Un HTTP que ignore el aborto tampoco escribe datos obsoletos tras un cambio de scope; su error anterior no se presenta como error actual.
- El indicador global de carga se recalcula desde las peticiones pendientes, evitando el falso `false` al acabar una de dos conversaciones.
- `src/services/MainAPI/whatsappApi.ts`: opción `AbortSignal` hacia Axios; conserva ruta, auth y contrato de respuesta.
- `src/store/__tests__/whatsappMessageFetch.test.ts`: **10 escenarios sintéticos**: deduplicación y refresco, medios/eventos recibidos durante fetch, estado de mensaje, contador unread, limpieza de sesión, reset, dos conversaciones simultáneas, fallo tardío y recuperación tras error.

No se cambian entidades, esquemas, reglas financieras, permisos, RLS, contratos ni mecanismos de envío. El backend ya acepta CancellationToken en el endpoint.

**CI:** [Admin Frontend CI](https://github.com/savelasquezs/senorArrozFront/actions/runs/40341272485) — resultado de la versión posterior a la corrección TS pendiente de verificar. La primera ejecución [40341040831](https://github.com/savelasquezs/senorArrozFront/actions/runs/40341040831) reveló **TS2454 (variable de cierre de promesa sin asignación definitiva)**, que se corrigió con una declaración definida antes del `finally` en commit `93236c5`. No se presenta la ejecución fallida como éxito.

La deduplicación evita repetir la **solicitud concurrente**, pero no disminuye el costo de consultas no solapadas ni elimina el trabajo por medio que haga el servidor. Los ensayos con promesas no equivalen a un benchmark de PostgreSQL o HTTP real.
