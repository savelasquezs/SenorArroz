## 1. Flujo, alcance y causa raíz

POS (tabla/listado y detalle de pedidos) → `AssignDeliveryModal.vue` → `orderManagementApi.options(orderId)` → `GET /api/orders/{id}/operation-options` → `OrderManagementController.Options(CancellationToken)` → `OrderManagementService.RequireOrder/GetOptions` → EF Core/PostgreSQL. La operación de guardar sigue `orderApi.assignDelivery/unassignDelivery` → `OrdersController` → `AssignDeliveryManHandler/UnassignDeliveryManHandler` → `OrderRepository` y `IDeliveryRouteWorkflowService`, con notificaciones post-commit existentes.

**Problema demostrado por código:** la carga de opciones se iniciaba en `onMounted` o al abrir. `fetchDeliverymen` no tenía abort ni identidad/generación de petición; al resolver comprobaba solo `props.open` e igualdad del ID, por lo que una solicitud anterior para el **mismo pedido** cerrada/reabierta podía sustituir opciones más recientes, o apagar `loading` durante la nueva lectura. Al cambiar de pedido con el modal todavía abierto, faltaba un watcher de `order.id` para restablecer selección y consultar los domiciliarios correctos. Una mutación en vuelo podía emitir `updated`, `statusChanged`, `close` y toasts después de cambiar el pedido, sin validar contexto.

**Segunda causa raíz verificada:** el backend `AssignDeliveryManHandler` ya actualiza `Ready → OnTheWay` al asignar y devuelve el pedido actualizado. En `OrderDetailContent.vue`, el evento `updated` ya aplicaba ese estado al store; sin embargo, también escuchaba `status-changed` y ejecutaba `useOrderStatusChange.executeStatusChange`, enviando un segundo `PUT /api/orders/{id}/status` tras el `PUT /api/orders/{id}/assign-delivery`. Son dos mutaciones para la misma transición cuando la asignación se inicia desde el detalle. `OrdersList.vue` escucha el mismo evento pero solo limpia un estado pendiente, sin mandar un segundo PUT; esa conexión se conserva. Es una secuencia derivada del código, no una traza productiva.

El endpoint ya propagaba `CancellationToken` desde MVC hasta las consultas EF: no se requiere cambio de backend. Su lectura consulta pedido, sucursal de despacho, bancos normales, apps y domiciliarios activos de esa sucursal, mediante `AsNoTracking` y proyecciones. El selector necesita solo domiciliarios; evitar las consultas de bancos/apps exigiría un endpoint dedicado o cambio de contrato, fuera de la corrección mínima de hoy. No se demuestra N+1 en este camino; el método ejecuta consultas secuenciales para recursos distintos. Sin EXPLAIN/índices productivos, no se propone SQL ni caché de opciones que pudiera quedar desactualizada.

SignalR puede actualizar el pedido tras una mutación; no se modifican sus eventos ni grupos, procesos de rutas, Flutter, Next.js, Print Agent ni servicios externos. La selección y desasignación conservan las reglas actuales (roles, sucursal, estado, conductor activo, almuerzo y flujo de ruta). Se evita solamente aplicar una **respuesta vieja en la UI**, no se cancela un PUT que el servidor ya pudo confirmar.

PRs existentes considerados: M15-F01 (Vue #55, API #80, Docs #81), M12-F01 (API #64/Vue #42), M09-F03 y otros PR abiertos. No existe un PR M15-F02 en progreso. No se modifican archivos de los PRs de M15-F01: la corrección afecta el modal, el consumidor de detalle de pedido, el cliente HTTP y pruebas pertinentes.

| Métrica | Antes | Fuente y límites |

| HTTP de opciones para abrir una vez | Una llamada al entrar en el modal | Camino del código; no es medición Network |

## 3. Corrección mínima en rama

- `src/services/MainAPI/orderManagementApi.ts`: parámetro opcional `AbortSignal` para `options`, enviado por el método `BaseApi.get`; API y contrato permanecen idénticos.
- `src/components/orders/AssignDeliveryModal.vue`: un único watcher inmediato de apertura, ID y sucursal; invalidación por generación, aborto de consultas antiguas, limpieza de estado y selección por contexto, descartando completados/errores obsoletos. Cancelación al desmontar.
- Al guardar: capturar pedido/domiciliario/contexto, proteger contra doble envío **por ID aun tras cerrar/reabrir**, y emitir cambios o mensajes **solo** si instancia/contexto permanecen vigentes. No interrumpir la mutación ya enviada al servidor.
- `src/components/orders/OrderDetailContent.vue`: quitar únicamente el listener `status-changed` que enviaba un segundo PUT de estado (el backend asignador ya lo hizo). Conservar `updated` que aplica el pedido y el listener no mutador de OrdersList. Se reduce de dos a una petición mutadora por asignación desde detalle para un pedido Ready, según análisis del código.
- `src/services/MainAPI/__tests__/orderManagementOptionsCancellation.test.ts`: pruebas de la señal HTTP opcional y compatibilidad.
- `src/components/orders/__tests__/OrderDetailContent.test.ts`: regresión que emite los eventos del diálogo y verifica que `OrderDetailContent` actualiza estado sin ejecutar `orderApi.updateStatus`.
- `src/components/orders/__tests__/AssignDeliveryModal.races.test.ts`: nueve regresiones sintéticas con promesas diferidas de cerrar/reabrir, cambiar pedido y volver a cargar, aborto, errores tardíos, guardado tardío, doble envío incluso tras reabrir y desasignación. No exponen datos privados ni utilizan sucursales reales.

**Pruebas/CI:** pendiente confirmar la ejecución final del nuevo PR. No declararlo listo hasta completar build/typecheck y suite. La auditoría documental y el propio PR se mantienen en borrador si las pruebas no pasan.

**Garantías:** sin nuevos permisos, sin accesos cross-branch, sin cambio de DTO, sin servidor desplegado, sin modificación de pago/stock/estado/rutas. No añadir caché global (lista de domiciliarios y almuerzos cambia durante el día).
