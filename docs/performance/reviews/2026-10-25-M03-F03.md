## 1. Flujo, causa y evidencia

Tres consumidores Vue acceden a `branchApi.getBranchById(id, true)` en modo operativo:
`src/store/branchPosSettings.ts` lee `maxFreeDeliveryDiscount`, `posCopyEtaMinMinutes`, `posCopyEtaRangeMinutes`; `AddressDeliveryFeeDialog.vue` usa nombre/latitud/longitud para distancia/tarifa; `CustomerAddressForm.vue` utiliza nombre/latitud/longitud para previsualización de ruta. La rama administrativa `src/store/branches.ts` llama sin el indicador y requiere el DTO completo.

Solicitud: `GET /api/Branches/{id}?forOrderCreation=true` → `BranchesController.GetBranch` (Authorize Cashier/Admin/Superadmin, `AllowCrossBranchOrderContext`) → `GetBranchByIdHandler` → `BranchRepository.GetByIdWithDetailsAsync`. En el código previo, incluso con `forOrderCreation=true`, se ejecutaba la ruta completa, con `Users.ThenInclude(PayrollExpense)`, `Neighborhoods`, `PrintSettings`; después cinco `CountAsync` y estadísticas de barrios. `BranchDto.Users` contiene `BranchUserDto` con nombre, correo, teléfono, rol y referencias de nómina. El modo cross-branch omitía `EnsureAccess(id)` intencionalmente para permitir cambiar la sucursal destino.

**Hallazgo demostrado por lectura de código:** el usuario autorizado para crear un pedido cross-branch podía recibir colecciones y atributos que los consumidores operativos no requieren, y la ruta cargaba colecciones y estadísticas que no se utilizan. **No demostrado:** extracción real de información por un usuario, cantidad de SQL exacta del handler completo en producción ni impacto porcentual de latencia/costo.

El backend mantiene filtros globales EF de tenant y políticas RLS PostgreSQL; el modo cross-branch debe **conservar** ese aislamiento. `OrderHub` asocia grupos de SignalR por sucursal y tenant al conectarse; no se modifica el hub ni sus flujos. No se cambia Flutter GPS, Next.js checkout, Print Agent ni workers. Se consultaron PR abiertos: API #53 se centra en Rappi y no se cruza con el endpoint.

## 3. Corrección preparada en rama (sin merge)

`BranchesController.GetBranch` mantiene contrato y atributos. Para `forOrderCreation=true` envía `GetBranchOrderContextQuery`; para modo ordinario conserva `EnsureAccess` y `GetBranchByIdHandler` sin modificar. El handler nuevo consulta `db.Branches.AsNoTracking()` y proyecta exactamente **9 atributos operativos**: ID, nombre, dirección, latitud, longitud, actividad, descuento de domicilio, minutos ETA mínimo y rango. Deja vacías las colecciones y sin datos de impresión/nómina/estadísticas, manteniendo `ApiResponse<BranchDto>` compatible con el frontend. Sin `IgnoreQueryFilters`, sin carga de navegación, sin caché nueva ni cambios a roles.

**Archivos de código:** `SenorArroz.API/Controllers/BranchesController.cs`, `SenorArroz.Application/Features/Branches/Queries/GetBranchOrderContextQuery.cs`, `SenorArroz.Tests/CrossBranchOrderContextTests.cs`.

**Regresiones incluidas:** proyección segura y campos requeridos, aislamiento de tenant, cancelación, PostgreSQL efímero con interceptor SQL sin joins a usuarios/barrios y dos pruebas del controlador para verificar que el indicador usa el handler seguro y el modo administrativo aplica `EnsureAccess`. La suite PostgreSQL ordinaria de RLS sigue siendo responsable de verificar las políticas; `EnsureCreated` del test aislado no instala políticas RLS productivas.

**CI:** [Backend CI del PR](https://github.com/savelasquezs/SenorArroz/pull/62/checks). Resultado pendiente al abrir el informe; por ello sigue en borrador. No se ejecutó .NET ni PostgreSQL en el contenedor local, que no tiene SDK/Docker.
