## 1. Flujo y evidencia de causa raíz

`ExpensesView.vue` → `expenseHeaderApi.getExpenseHeaders` → `GET /api/expenseheaders` → `ExpenseHeadersController.GetExpenseHeaders` → MediatR `GetExpenseHeadersHandler` → `ExpenseHeaderRepository.GetPagedAsync` → EF Core / PostgreSQL (`ExpenseHeaders`, `ExpenseDetails`, `Expenses`, categorías, `ExpenseBankPayments`, bancos y proveedores). El handler complementa datos vinculados con `ExpenseHeaderLinkedAdvancePopulator`. No se localizó dependencia directa de SignalR, Flutter, Next.js o Print Agent en este listado. Los PR abiertos M06-F02, M03-F03, M12-F01 y Rappi #53 se comprobaron antes de elegir el feature: ninguno corrige este flujo; Vue #42 modifica `OrdersList.vue`, no `ExpensesView.vue`.

**Defectos demostrados por inspección:** cuatro watchers de categorías, bancos, proveedores y texto podían emitir varias invocaciones de `fetchExpenses()` en una misma interacción de filtros. La función asignaba `expenses`, `totalCount`, estado `loading` y mensajes de error sin correlacionar qué petición correspondía al estado vigente: una respuesta tardía podía sobrescribir una posterior. Al cerrar o cambiar de filtro no se pasaba señal de cancelación al Axios. El controller enviaba `Send(query)` sin `CancellationToken`, aunque handler y repositorio ya aceptaban ese token.

**Alcance del análisis SQL:** la consulta del repositorio usa `AsNoTracking`, varias inclusiones EF y paginación. Hay riesgo de carga por relaciones múltiples, pero no se afirma N+1 ni costo exacto sin trazas SQL o `EXPLAIN (ANALYZE, BUFFERS)` en entorno controlado. Sin indicación de cambiar índices, caché, RLS o esquema en esta corrección. Las mutaciones de gastos, liquidaciones y cálculos financieros permanecen intactos.

## 3. Corrección mínima en ramas independientes

**Vue:** watcher único con `flush: 'post'` para filtros combinados, debounce de 300 ms conservado para texto; fingerprint de página/tamaño/filtros/orden/fechas + usuario/rol/sucursal; reutiliza promesa de un mismo filtro en vuelo y fuerza recarga explícita al pulsar actualizar. AbortController invalida trabajo anterior; respuestas y errores tardíos no modifican pantalla. Cambios locales por creación/eliminación invalidan lecturas anteriores para evitar resucitar filas borradas. Al desmontar cancela solicitudes y temporizador. Se preserva el endpoint, paginación, orden y formulario existentes.

**API:** GET listado recibe CancellationToken de ASP.NET y lo pasa a MediatR, que ya lo transmite a repositorio EF/PostgreSQL. No se modifica ninguna otra ruta ni condición de autorización. La cancelación no deshace una consulta que ya finalizó, pero permite abandonar trabajo aún cancelable.

**Archivos de código:** `src/views/ExpensesView.vue`, `src/services/MainAPI/expenseHeaderApi.ts`, `src/composables/createLatestExpenseHeadersQuery.ts`, sus pruebas de Vitest, `SenorArroz.API/Controllers/ExpenseHeadersController.cs` y prueba xUnit de controller. **No se tocaron** otras funciones de caja, pagos ni tablas.

**Regresiones incorporadas:** solicitudes idénticas simultáneas, respuestas fuera de orden, error obsoleto, refresh forzado, nuevo contexto de sucursal, reintento tras error, cancelación de lectura al mutar un gasto, desmontaje, señal Axios y propagación de cancellation token en MediatR. **Evidencia final de CI comprobada:** [Vue Actions #40336895968](https://github.com/savelasquezs/senorArrozFront/actions/runs/40336895968) **SUCCESS** en head `150bdb467c4dd7f336dceb2ea3823b778a8003d4`: typecheck/build y **864/864 pruebas Vitest en 133 archivos**, con las 8 pruebas nuevas del coordinador y 1 de transporte. `npm ci` notificó 12 vulnerabilidades preexistentes (4 moderadas y 8 altas), no corregidas en este PR. ## 5. Base de datos, compatibilidad y reversión

**Migración: NO. Scripts SQL pendientes: ninguno.** No se añaden índices ni columnas ni se altera RLS, EF mapping, datos o restricciones. No hay backfill, ni hay que ejecutar comandos SQL en Railway. Los backups habituales siguen vigentes; no se requiere backup de migración para estos cambios.

El frontend es compatible con la API actual: enviar AbortSignal a Axios no cambia parámetros ni JSON de la solicitud. El backend es retrocompatible y solo propaga la cancelación en GET. No se requiere un orden estricto para fusionar **tras aprobación**; para aprovechar cancelación hasta PostgreSQL, conviene integrar la API antes del frontend. Reversión: PR revert de cada commit (frontend primero si se desea), sin operación de rollback en BD.
