## 1. Evidencia y causa raíz

1. `KitchenView.vue` llamaba a `ordersStore.fetch({page:1,pageSize:100,forKitchen:true})`; posteriormente `ensureOrderDetails` emitía `fetchDetail(id)` para cada pedido sin caché. Por inspección, primera carga con `N` pedidos sin caché equivale a 1 + N HTTP desde esta vista. Esto **no** es una medición de tráfico real en Railway.
2. La carga de cocina ocultaba pedidos elegibles más allá de la primera página de 100.
3. `NewOrder`, `ReservationReady`, `OrderModified` y `OrderCancelled` podían iniciar recargas superpuestas de lista; la ruta de notificación TTS consultaba detalles otra vez.
4. El resumen horario paginaba búsquedas históricas por estados Taken/InPreparation sin filtrar por el día de resumen, y recuperaba detalles ausentes mediante múltiples HTTP.
5. `OrderRepository.GetAllAsync` incluía `BankPayments` y `AppPayments` para tarjetas de cocina que no los usan.
6. `src/services/MainAPI/orderApi.ts` omitía `SortBy/SortOrder` en el mapeo de parámetros GET aunque el controller los acepta; el nuevo recorrido de varias páginas exige orden único.

**Flujo:** `KitchenView.vue` → `ordersData.ts` / `orderApi.ts` → `OrdersController.GetOrders` → `GetOrdersHandler` → `OrderRepository.GetAllAsync` y EF Core → PostgreSQL. SignalR reutiliza un hub compartido con listeners por componente. Para el resumen: nuevo `OrdersController.KitchenSummary` → `GetKitchenSummaryHandler` → `order` y `order_detail/product/category`.

**Permisos:** endpoint de resumen restringido a Kitchen/Admin/Superadmin; branch resuelta por contexto de sesión y usuario (cajeros no acceden); queries EF usan filtros tenant y RLS. Los IDs para carga de líneas proceden únicamente de una página autorizada. Verificación funcional y multitenant real aún pendiente.

## 2. Cambios implementados

**Backend PR #25**
- Nuevo `OrderDto.KitchenDetails` nullable/omitido fuera de cocina para preservar el JSON de listados generales.
- `GetOrdersHandler` toma la página autorizada y carga todas sus líneas con **una consulta** AsNoTracking/Include(Product.Category), entregando notas, cantidades y categorías completas. Propaga CancellationToken.
- En `GetAllAsync(forKitchen:true)` se evitan relaciones bancarias/apps no usadas en las tarjetas.
- Nuevo `GET /api/orders/kitchen-summary?date=YYYY-MM-DD` con DTO ligero, filtros en PostgreSQL por (PrepareAt ?? CreatedAt), fecha Colombia y estados vigentes; carga líneas por lote.

**Vue PR #18**
- `syncKitchenPageDetails` usa las líneas embebidas como fuente actual, reemplaza caché obsoleta, distingue campo omitido de `[]`; conserva fallback temporal al API anterior.
- Recorre todas las páginas de la cola de cocina y publica la lista completa tras finalizar; ordena por ID de forma única.
- Serializa recargas y agrupa eventos simultáneos; evita que una recarga superpuesta sea el estado final. Notificaciones usan datos de la página para reducir `fetchDetail`.
- Resumen consulta el nuevo API filtrado por fecha y evita la respuesta tardía de filtros previos. Si el backend aún no tiene esa ruta (HTTP 404), usa temporalmente la ruta histórica.

## 3. Impacto lógico y limitaciones

| Métrica | Antes (por lectura de código) | Con los PR propuestos | ¿Medido? |
|---|---|---|---|
| HTTP en carga inicial con N tarjetas sin caché (<=100) | 1 + N | 1 por página de 100, sin detalle por tarjeta | No |
| HTTP si hay >100 tarjetas | 1 + N, pero solo 100 tarjetas cargadas | ceil(N/100) listados; páginas completas, sin GET de detalle por tarjeta | No |
| Resumen de día | Búsqueda histórica paginada + N detalles faltantes | 1 endpoint especializado con lectura de líneas por lote | No |
| SQL | Lecturas repetidas de pedidos completos | Filtrado por página/día + lectura de líneas por lote | No |
| p50/p95, egress, CPU, RAM | Sin medir | Sin medir | No |

La transferencia de detalles en el listado aumenta los bytes de esa respuesta, pero reemplaza múltiples respuestas de pedido completo. **No se afirma una reducción neta medida**. No hay EXPLAIN/ANALYZE ni evidencia para crear índices nuevos.

- **Ejecutadas localmente:** ninguna; no hay `dotnet` ni dependencias Vue instaladas en el entorno de trabajo. **CI GitHub pendiente de resultado verificable**. Mantener los PR en borrador hasta que todo pase.
- **Riesgos prioritarios:** revisar contrato JSON de estados/categorías; permisos de sucursal y tenant; datos de reserva en hora Colombia; concurrencia de cambios de estados, pagos y listas; volumen de registros y egress; compatibilidad durante despliegue backend → Vue.
