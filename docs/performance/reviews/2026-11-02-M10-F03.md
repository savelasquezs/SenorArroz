## 1. Flujo, evidencia y causa raíz

`src/views/OrderDetail.vue` escucha `route.params.id`, llama `ordersData.fetchById(id)`, que usa `orderApi.fetchDetail(id)` → `GET /api/orders/{id}/details` → `OrdersController.GetOrderWithDetails` → `GetOrderWithDetailsHandler` → `OrderRepository.GetByIdWithFullDetailsAsync` → EF Core / PostgreSQL.

El repositorio usa `AsNoTrackingWithIdentityResolution` con `Include` sobre Branch, TakenBy, Customer, Address/Neighborhood, LoyaltyCycleStep, DeliveryMan, DeliveryRoute/Stop, OrderDetails/Product/Category, BankPayments/Bank/Branch y AppPayments/App/Bank/Branch. Es una carga con varias colecciones; no se determinó el plan SQL, filas multiplicadas, índices ni N+1 real. No cambiar `AsSplitQuery` ni índices sin medición y evaluación de consistencia.

**Defecto confirmado por flujo:** al navegar rápidamente entre IDs, `OrderDetail.vue` solo incrementaba `detailRequest` y descartaba el resultado visual antiguo, pero no cancelaba el GET iniciado. Además, su spinner dependía de `ordersData.isLoading`, estado compartido con otros consumidores del store, por lo cual podía seguir visible aunque terminara la solicitud de la ruta actual. El store protegía `current` con generación, pero no validaba un `AbortSignal` al recibir datos. El controlador no pasaba `CancellationToken` a MediatR pese a que handler/repository sí lo admitían.

En el mismo módulo, `useOrderSnapshotUpdates` usa SignalR y solicita `fetchDetail` para contrastar versión; esa consulta queda fuera de la corrección, y su posible deduplicación/cancelación requiere pruebas separadas para no alterar ediciones concurrentes. El cliente web público, Flutter y Print Agent no cambian. No se encontraron motivos para modificar pagos, inventario o mutaciones de pedidos.
