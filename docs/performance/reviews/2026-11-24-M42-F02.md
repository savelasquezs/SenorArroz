## 1. Flujo y causa raíz

- Next/Workers `helpers/storefront-public-data.ts`: readPublicCatalog → getPublicResponse("/public/storefront/catalog", fetcher, config); fetch con no-store y credencial de servicio en cabecera, timeout de 15 s. El lector consume response.text(), valida, normaliza y calcula revisión; dispone coordinación/memoización por catálogo. No alterar ese comportamiento.
- API `SenorArroz.API/Controllers/PublicStorefrontController.cs`: GET catalog; esquema StorefrontApiKey, rate limit storefront-catalog y ResponseCache(NoStore = true, Location = None).
- `SenorArroz.API/Services/StorefrontCommerceService.cs`: GetCatalog lee Products activos con categorías y perfiles comerciales (AsNoTracking, Includes), sucursales elegibles, disponibilidad de inventario por sede de forma secuencial con el mismo DbContext y horarios agrupados. Devuelve PublicCatalogDto con grupos, productos/precios/disponibilidad, datos comerciales públicos de sucursales/horarios, ciudades y reglas públicas. No refleja query, sesiones ni credenciales.
- `SenorArroz.API/Hosting/ApiHost.cs`: configuración de controladores y pipeline sin AddResponseCompression ni UseResponseCompression; Kestrel no comprime por sí mismo estas respuestas. El JSON puede repetirse en refrescos legítimos. **Se confirma ausencia de compresión en el proceso API, no que Railway/Cloudflare entreguen necesariamente bytes sin comprimir.** No se realizó petición autenticada a producción ni se usaron secretos.
- SQL: no cambia la forma de leer catálogo, consultas de inventario ni horarios, índices, RLS o transacciones. No hay conteo SQL o EXPLAIN medido. No se atribuye un N+1 al flujo sin traza; los HTTP duplicados no son el objetivo de esta revisión (ya hay coordinación en web).
- Flutter, POS Vue y Print Agent no son consumidores directos del GET de catálogo storefront identificado. WhatsApp Flow llama al servicio de catálogo internamente, no pasa por middleware HTTP; SignalR y rutas de WhatsApp no se modifican.

No aplica a otros endpoints, SignalR, cotizaciones, pagos, OTP ni sesiones. HTTP sin encoding negociado sigue en identidad; no se cambia no-store ni se incorpora almacenamiento/caché. No son pruebas de un proxy real ni de autenticación real; el rechazo es simulado y los tests existentes cubren los controladores.

Se excluye compresión global y se limita a contenido comercial no personalizado; preservar esta propiedad si el contrato cambia.
