## 1. Flujo y causa raíz demostrada

Ruta auditada: `CustomerForm.vue` / pantallas de clientes → `useCustomersStore.update` → `customerApi.updateCustomer` → `PUT /api/customers/{id}` (`CustomersController.UpdateCustomer`, autenticado + roles) → `UpdateCustomerHandler` → `CustomerRepository` → EF Core/PostgreSQL (`Customers`, `CustomerPhones`, direcciones/servicios; estadísticas sobre `Orders`). Al terminar el handler se aplican resúmenes de pedidos y previas de fidelización. No se disparan operaciones SignalR ni de rutas/Flutter/Next.js/Print Agent desde esta corrección.

Defecto comprobado en `main`:

1. `CustomerRepository.UpdateAsync` ya realiza `GetByIdWithAddressesAsync(customer.Id, token)` tras `SaveChangesAsync` y **devuelve la entidad rehidratada**. `UpdateCustomerHandler` descarta ese resultado y vuelve a ejecutar `GetByIdWithAddressesAsync` antes de mapearlo. Es una segunda invocación de lectura de grafo (la implementación usa `AsSplitQuery` y varias relaciones): el número exacto de comandos SQL de cada invocación no se ha medido.
2. El handler llama a `PhoneExistsAsync` por cada teléfono móvil del formulario, incluso si ambos números ya son del mismo cliente (por ejemplo, al cambiar solo el nombre). Hasta dos comprobaciones `EXISTS` redundantes en cada actualización sin cambios de identidad.
3. Esas dos comprobaciones de teléfono omitían propagar el `CancellationToken` del request, aunque la interfaz y su repositorio ya lo admiten.

El camino desde `CustomersList.vue` ejecuta un `PUT /api/customers/{id}` y después un **GET del listado** mediante `load()`. No se elimina esa recarga: una edición de nombre o del estado activo puede cambiar el conjunto filtrado, el orden y la paginación. `CustomerDetailModal.vue` reutiliza el mismo `customersStore.update`, pero emite el cliente resultante al padre. No se detectó evidencia suficiente para retirar estas recargas de vista como duplicación redundante. Este PR no cambia peticiones del frontend. El flujo CRUD existente ya protege tenant en el repositorio y valida unicidad de números móviles dentro del tenant. Las líneas 604 son contacto administrativo, no identidad móvil, y no pasan por `PhoneExistsAsync`.

PRs abiertos revisados: M12-F01 (API #64/Vue #42/docs #65) y M03-F03 (API #62/docs #63). Ninguno es una corrección en curso de M06-F02. El M06-F01 del 25 de octubre ya fue fusionado (API #66/Vue #43); M06-F05 se revisó previamente. Esta corrección modifica únicamente el handler de edición y sus pruebas.

## 3. Corrección en rama

- `SenorArroz.Application/Features/Customer/Commands/UpdateCustomerHandler.cs`: usar el objeto ya rehidratado que devuelve `UpdateAsync`, manteniendo el mapeo, los agregados estadísticos y la vista previa de fidelización. No altera DTO/contrato ni el repositorio de persistencia.
- Normalizar los **móviles existentes** una sola vez; solo comprobar `PhoneExistsAsync` para móviles realmente nuevos respecto de ambos números previamente asociados. Cuando sí se comprueba, pasar el `CancellationToken` al repositorio. El chequeo sigue siendo tenant-scoped y excluye el cliente editado.
- `SenorArroz.Tests/CustomerUpdateReadTests.cs`: regresiones para lectura redundante, conservación de direcciones/estadísticas, cero verificaciones de números existentes (incluida variante +57), una comprobación de teléfono nuevo con token y rechazo de teléfono de otro cliente.

**Garantías:** `UpdateAsync` continúa guardando y consultando el grafo una vez; la lógica de `CustomerPhones`, autorización, aislamiento tenant/RLS, sucursales y pagos no se toca. Los teléfonos de otro cliente siguen bloqueados. Si un teléfono se cambia, se sigue consultando al repositorio. Se preservan los mensajes de error de negocio.

**Alternativa descartada:** cambiar `CustomerRepository.UpdateAsync` para eliminar su propia rehidratación. Eso afectaría a cualquier otro consumidor de su contrato y aumentaría riesgo; es más seguro reutilizar el resultado en el handler.
