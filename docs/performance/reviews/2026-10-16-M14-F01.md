## 1. Flujo y causa raíz

- Vue `src/services/MainAPI/printJobsApi.ts` envía `POST /api/branches/{branchId}/print-jobs` a `BranchPrintJobsController.Enqueue`; este valida rol, tipo, sucursal y llama a `PrintQueueService.EnqueueAsync` (cocina/caja) o `EnqueueDeliveryAsync` (domicilio).
- `PrintQueueService.EnqueueAsync` carga entidades `Orders` con `AsNoTracking` e `Include`, incluida la columna mapeada `Order.Notes`. Ejecutaba otra SELECT sobre los mismos IDs para volver a leer `Notes` (líneas 115-125 de main), sin necesidad.
- Después, por **cada pedido con cliente**, `BuildLoyaltyKitchenSnapshotAsync` hacía COUNT de entregas, MAX del ciclo activo y, si había ciclo, SELECT de etiqueta: hasta **3 × N** viajes SQL de fidelización por lote de N pedidos con cliente.
- El encolado persiste `print_job` antes de avisar por SignalR. El agente Windows tiene ruta de claim directo ante evento: `Worker.ClaimAndDispatchAsync` no filtraba el tipo notificado contra `GetEnabledKinds`; el GET general de pendientes sí pasaba `kinds`.
- El contexto tenant de EF y las verificaciones de pertenencia a sucursal se mantienen. Roles del endpoint: Superadmin/Admin/Cashier/Kitchen/Deliveryman, con restricciones de tipo para Kitchen y Deliveryman.

## 2. Corrección implementada (aún sin merge)

- **API #29:** elimina la segunda SELECT de `Notes`. Reemplaza llamadas individuales de fidelización por un COUNT agrupado por `CustomerId` y una única lectura de pasos activos por sucursal. Reutiliza `LoyaltyDeliveriesPerReward` y `PrintTicketPayloadBuilder`; retira dependencias no usadas. Añade `LoyaltyElapsedMs` a la telemetría existente, sin cambiar `OrderQueryElapsedMs`.
- **Agente #1:** la ruta de notificación de SignalR solo reclama tipos que ya están en la lista de impresoras habilitadas; sigue recuperando por GET los tipos elegibles y preserva polling de respaldo. Incluye workflow de CI mínimo porque el repo no tenía `.github/workflows`.
- **Sin nuevas interfaces, servicios, DTOs ni cachés.** La proyección existente de domicilios no se modifica.

## 4. Riesgos, exclusiones y control

- Una lectura nueva con `GroupBy` debe probar traducción relacional PostgreSQL (prueba añadida para ello). Los conteos siguen aplicando filtro tenant y abarcan pedidos entregados del cliente, como el repositorio anterior. Los pasos se restringen a sucursal y activos.
- El filtro de tipo del agente es **operacional**, no una autorización adicional en servidor: el token del agente continúa vinculado a la sucursal.
- No se aplicó `AsSplitQuery()` sin estadísticas de cardinalidad de colecciones; podría añadir viajes SQL innecesarios. No se alteró el polling desconectado de 1–2 s sin medición de costo/latencia de impresión. Ambos quedan para M14-F02.
- Un test exitoso no sustituye una prueba de impresión real con observaciones, varios pedidos, regalos y dos agentes con impresoras distintas.
