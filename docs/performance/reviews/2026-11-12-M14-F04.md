## 1. Flujo y causa raíz

1. Vue `src/services/MainAPI/printJobsApi.ts` y Flutter `lib/core/api/api_constants.dart` referencian `POST /api/branches/{branchId}/print-jobs` para encolar; `BranchPrintJobsController.Enqueue` valida autorización y `PrintQueueService.EnqueueAsync/EnqueueDeliveryAsync` persiste `print_job` (`pending`) y avisa por SignalR.
2. `Worker.ClaimAndDispatchAsync` atiende señal `PrintJobsAvailable` o polling. `GET .../{jobId}/claim` / `GET .../pending` autentican token, aplican tenant scope y reclaman atómicamente `pending → processing`. Claim masivo usa `FOR UPDATE SKIP LOCKED`, índice parcial de trabajos pendientes ya documentado, sin cambio de plan o DDL en esta revisión.
3. `PrinterJobDispatcher` serializa trabajos por impresora. `PrintJobProcessor.ProcessAsync` prepara bytes, ejecuta `IRawPrinter.Send` y hace `POST .../{jobId}/complete`. **Defecto confirmado en main:** el mismo `try/catch` envolvía render, envío RAW y confirmación HTTP. Si la impresora aceptó bytes pero la confirmación falla o se pierde la respuesta, el catch invoca `POST .../{jobId}/fail` y puede cambiar `processing → failed`. Esto confunde un fallo de transporte HTTP con fallo físico de impresión.
4. `BranchPrintJobsController.Complete/Fail` autentican el agente por sucursal/tenant y llaman `PrintQueueService.TryCompleteJobAsync/TryFailJobAsync`: ambas leen `print_job` con EF Core y, si está en `processing`, actualizan `status`, `completed_at` y, en fallo, `error_message`. No se demostraron N+1, índices ausentes ni CPU/RAM/egress medidos en este subflujo.
5. **Hechos vs hipótesis:** el camino de código produce el POST `fail` indebido después de fallo de POST `complete`; no existe evidencia de cuántas veces ocurrió en producción, de una impresión duplicada real ni del destino de trabajos `processing` huérfanos. No se modifican las políticas de reencolado ni tiempos de polling.

## 3. Cambio mínimo y pruebas

- En `src/SenorArrozPrintAgent/PrintJobProcessor.cs`, solo los errores de render o `IRawPrinter.Send` notifican `FailAsync`. **Después de que el spooler acepta los bytes, una excepción de `CompleteAsync` nunca llama `FailAsync` ni reenvía RAW.**
- Reintento limitado del acuse: máximo tres POST `complete` (primer intento + dos reintentos separados 200/400 ms), con timeout de 8 s por intento frente al timeout HTTP general de 2 min; solo ante fallo de red, timeout o HTTP 408/429/5xx. HTTP 401/403/404 u otros errores permanentes no reintentables se registran. Si persiste la ambigüedad, el log pide conciliación manual; no se declara éxito físico. El acuse puede ocupar hasta aproximadamente 24,6 s en tres timeouts consecutivos, durante los cuales la cola de esa impresora sigue serializada.
- `tests/SenorArrozPrintAgent.Tests/PrintJobProcessorTests.cs` añade tres casos: fallo de red persistente después del spool (0 `fail`, solo 1 `spool`), error transitorio recuperado (2 `complete`, 1 `spool`) y 404 sin reintento. Conserva pruebas de envío exitoso y fallo real de spooler.
- **CI comprobada** para head `2662d915`: [Print Agent CI #3](https://github.com/savelasquezs/senorArrozPrintAgent/actions/runs/43223314205), `dotnet test SenorArrozPrintAgent.sln -c Release` con **18 aprobadas, 0 fallidas, 0 omitidas** en Ubuntu/.NET 9. ## 5. BD, riesgos, despliegue y rollback

- **Migración SQL: no aplica.** Sin tablas/índices nuevos, backfill, cambios EF o RLS. `print_job` conserva `pending/processing/done/failed`, y el índice parcial existente no se toca.
- **Riesgo residual:** incluso con reintentos, si el acuse se pierde permanentemente, el trabajo puede quedar `processing` y requerir conciliación. Un 404 podría significar acuse anterior exitoso, cambio de estado o trabajo inexistente: no asumir estado `done`. La recepción por spooler no demuestra papel impreso. No introducir reintentos ciegos de impresión.
- **Prueba obligatoria antes de merge/publicación:** Windows con impresora RAW, un ticket real de pruebas, simulación de pérdida de respuesta de `complete` y fallo real de spooler. Verificar 1 solo job spool, 0 `fail` cuando el spooler aceptó, reintento de confirmación, visibilidad de error persistente y separación por sucursal/tenant; no utilizar pedidos de clientes reales.
- **Orden de aprobación:** (1) revisar PR #3 y la CI; (2) validar físicamente en entorno aislado; (3) revisar/fusionar el PR documental y de código con autorización; (4) publicar el agente Windows controladamente y verificar logs/impresión. No tocar la API ni DB productivas para este cambio.
- **Reversión:** restaurar versión anterior del agente mediante el procedimiento Windows y comprobar estado/impresiones, considerando que reintroduce el defecto; no hay rollback SQL. Comparar casos anónimos de error/acuse y tiempos luego de la publicación aprobada.
