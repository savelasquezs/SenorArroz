## Flujo examinado
- Vista `senorArrozFront/src/views/OrdersList.vue`: montaje, consultas y filtros; `useOrderManagementUpdates` notifica cambios de pedidos, reconexiones y retorno a la vista; `searchOrdersOnce` deduplica consultas iguales en curso por `[workspaceBranchId, activeTab, requestBody]`.
- Cliente `src/services/MainAPI/orderApi.ts`: `POST /api/orders/search`.
- API `SenorArroz.API/Controllers/OrdersController.cs` → `SearchOrdersHandler` (filtros por usuario/sucursal y fecha Colombia) → `OrderRepository.SearchOrdersAsync` (EF Core y PostgreSQL).
- Carga inicial normal ya usa una consulta de pedidos, más peticiones independientes para bancos, apps y destinos remotos; **no afirmar que estas consultas de diferentes recursos son HTTP duplicados**.
- La lista de domiciliarios se deriva de la página principal si contiene todo el día sin filtros. Cuando está paginada/filtrada, la vista hace una búsqueda secundaria de pedidos tipo Delivery, por páginas, para poblar un filtro completo. Antes esa ruta usaba `orderApi.searchOrders` directamente, eludiendo la deduplicación ya existente.

## Problemas confirmados por inspección del código
1. **SQL / COUNT innecesario:** `SearchOrdersAsync` ejecutaba `COUNT(*)` aun si `page=1` y la lista paginada de IDs era estrictamente menor que `pageSize`, por lo que el total ya era conocido. Afectaba todas las búsquedas de primera página incompleta.
2. **HTTP solapado en filtro de domiciliarios:** en la ruta alternativa que recupera domiciliarios exhaustivamente, dos operaciones concurrentes del mismo rango y alcance podían emitir `POST /api/orders/search` idénticos. La consulta principal ya se deduplicaba, pero esa ruta auxiliar no. Esto no implica que siempre hubiera doble solicitud ni que una búsqueda de todos los domiciliarios sea innecesaria.

## Correcciones implementadas
- Backend `OrderRepository.cs`: mover el `CountAsync` después de obtener IDs y usar `ids.Count` si primera página incompleta; mantener `COUNT(*)` para páginas llenas, posteriores y fuera de rango. No se cambian filtros, orden ni respuesta `PagedResult`.
- Frontend `OrdersList.vue`: reutilizar `searchOrdersOnce(scope, buildDeliverymenInRangeSearchBody(...))` en el fallback de domiciliarios. Deduplicación **solo durante el vuelo**, sin TTL ni caché de resultados; conserva cambios en tiempo real, búsquedas paginadas y contextos local/remoto.
- Prueba backend `OrderSearchFirstPageCountTests.cs`: contrato de paginación para primera página incompleta/llena, página posterior y fuera de rango, más prueba de integración en **PostgreSQL real con interceptación SQL** que comprueba `COUNT(*)` **0 veces** para primera página incompleta/vacía y **1 vez** para página llena, posterior o fuera de rango. Esto corrige la observación P2 de la revisión automática del PR.
- Prueba frontend `OrdersList.remoteBranches.test.ts`: recarga de fechas solapada con un request pendiente del filtro Delivery; comprobar una sola búsqueda HTTP equivalente.
