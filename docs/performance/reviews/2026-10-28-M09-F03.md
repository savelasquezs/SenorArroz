## 1. Flujo y causa raíz

`Orders.vue` → `OrderSidebar` / `useOrderPersistence.onMounted` → `ordersDrafts.loadFromLocalStorage()` → `rehydrateCustomersFromDrafts()` → `customerApi.getCustomerById(id)` → `GET /api/customers/{id}` → `CustomersController.GetCustomer` → `GetCustomerByIdHandler` → `CustomerRepository.GetByIdWithAddressesAsync` → EF Core/PostgreSQL (Customers, Phones, Addresses, BranchServices, Neighborhood y consultas de estadísticas/fidelidad).

El endpoint principal **ya devuelve las direcciones**, incluso como array vacío. `CustomerDto.Addresses` se inicializa como lista y el handler utiliza `GetByIdWithAddressesAsync` con `Include(c => c.Addresses)`. Sin embargo, el store trataba `addresses: []` como «datos no cargados» y pedía otro `GET /api/customers/{id}/addresses`. Este segundo endpoint ejecuta `GetCustomerAddressesHandler`, verifica el cliente con `GetByIdAsync` y obtiene direcciones con `IAddressRepository.GetByCustomerIdAsync`. Es trabajo redundante para un cliente legítimamente sin direcciones.

Los IDs de clientes distintos ya se deduplican mediante `Set` antes de lanzar Promise.all. No es un N+1 dentro de una única consulta SQL: son solicitudes HTTP adicionales por cada cliente sin direcciones. La cantidad de clientes reales en esa condición, el SQL exacto y la latencia de Railway **no están medidos**.

El cambio se limita al frontend. No requiere endpoints, SignalR, Flutter, Next.js, Print Agent, caché compartida, trabajadores ni cambios PostgreSQL. El PR abierto M09-F02 (Vue #51, docs #74) cambia búsqueda de catálogo/ProductGrid, no los dos archivos de esta corrección. Se revisaron los demás PR abiertos y no hay otro PR M09-F03.

## 3. Corrección mínima en rama

- En `src/store/ordersDrafts.ts`, sustituir `if (!c.addresses?.length)` por `if (!Array.isArray(c.addresses))`. Distingue `[]` válido de un payload incompleto de versiones anteriores.
- Pruebas nuevas en `src/store/__tests__/ordersDrafts.rehydration.test.ts`: cliente con cero direcciones; cliente con direcciones; payload sin `addresses` que conserva fallback; cuatro borradores con tres clientes distintos (una carga por ID y ningún GET adicional cuando están completos).
- No cambia contratos, información fiscal, selección de dirección, pagos, descuentos, RLS, roles, persistencia local, ni numeración de tabs.
- Alternativas descartadas: desactivar completamente el fallback (rompería compatibilidad), añadir caché global (riesgo de scope y complejidad) o cambiar backend/índices sin medición.
