## 1. Flujo y causa raíz

`src/views/OrdersList.vue` (filtros de texto, páginas, pestañas local/remota y eventos de `useOrderManagementUpdates`) → `orderApi.searchOrders(body, signal)` → POST `/api/orders/search` → `OrdersController.SearchOrders` → MediatR `SearchOrdersHandler` → `IOrderRepository.SearchOrdersAsync` → EF Core/PostgreSQL (`Orders`, relaciones de clientes, pagos, reservas y rutas). El controlador ya transmite `CancellationToken` a MediatR; el handler lo pasa al repositorio, que lo usa en `ToListAsync` y `CountAsync`, así como en la carga de reservas.

**Causa concreta comprobada por código:** `searchOrdersOnce` utiliza dos mapas, `inFlightOrderSearches` y `searchControllers`, por clave `[workspaceBranchId, activeTab, body]`. Cuando cambia el filtro de A a B, se abortaba el controlador de A, pero **no se retiraba de `inFlightOrderSearches` la promesa A**. Si se regresa rápidamente a A mientras el transporte antiguo sigue pendiente, se reutiliza esa promesa abortada en lugar de emitir una nueva solicitud A. La vista previene la presentación de resultados obsoletos mediante `ordersRequest`, pero eso no repara la búsqueda válida que se vuelve a solicitar. También al escribir se invalidaba la generación de UI inmediatamente, mientras el HTTP antiguo seguía activo hasta el vencimiento del debounce de 300 ms.

Se inspeccionaron llamadas redundantes, paginación, filtros SQL y cancelación. El backend aplica `AsNoTracking`, consulta ligera de IDs, `COUNT(*)` solo cuando es necesario, `AsSplitQuery` y token de cancelación; no se encontraron pruebas que justificaran tocar índices, consultas o RLS para este defecto de estado cliente. Señales SignalR pueden iniciar refrescos, pero **el fallo de la promesa reutilizada pertenece al coalescedor Vue**, no a SignalR. Flutter, Next.js y Print Agent no consumen este estado de la vista.

La base del trabajo no contiene otro PR específico M10-F02. **Vue #42 (reservas)** modifica los mismos archivos `OrdersList.vue` y `OrdersList.remoteBranches.test.ts`, con hunks cercanos a `activateTab` y al cierre de la vista: si se integra primero, revisar el conflicto, rebasar y volver a ejecutar pruebas antes del merge. Los PR de despacho afectan otros archivos. No se infieren datos de producción de la inspección.
