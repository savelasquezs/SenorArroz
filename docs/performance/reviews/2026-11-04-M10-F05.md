## 1. Flujo y causa raíz

`OrderDetailContent.vue` expone `OrderProgressBar @status-click` y `AssignDeliveryModal @status-changed`. Ambos activan `useOrderStatusChange.handleStatusChange` o su función `executeStatusChange` → `orderApi.updateStatus(id,status,...,snapshot)` → `PUT /api/orders/{id}/status` → `OrdersController.ChangeOrderStatus` (`Authorize(Admin,Superadmin,Cashier,Kitchen,Deliveryman)`) → `ChangeOrderStatusCommand` / `ChangeOrderStatusHandler` → `OrderRepository.ChangeStatusAsync` → `SaveChangesAsync` en EF Core/PostgreSQL sobre `Orders` y entidades asociadas.

El handler carga el pedido para comprobar `OrderAccessRules.EnsureAccess`, transición y tenant; posteriormente gestiona transacción, posibles efectos en inventario y fidelización, rutas/impresión, y mensajes a otros usuarios. `BaseApi` ya dispone de `beginOrderMutation`/contador para señalar operación pendiente, pero este contador **no impide enviar** una segunda petición. `useOrderStatusChange` llamaba a `updateStatus` sin comprobar la petición en curso: dos clics durante la misma operación originaban dos PUT. El backend puede rechazar una transición inválida/conflictiva; no se afirma que dos estados o efectos secundarios lleguen a guardarse dos veces.

No se demuestra N+1 SQL ni ausencia de índices, pues el cambio solo previene solicitudes HTTP duplicadas desde un consumidor. La API de estado no usa SignalR como transporte de la mutación: puede publicar notificaciones/eventos para otros módulos. Flutter, Next.js y Print Agent no consumen **este composable Vue** y no requieren modificar sus repositorios. El listado POS `OrdersList.vue` utiliza otro código para transiciones y se deja fuera de este cambio pequeño (posible trabajo posterior), para evitar solapar el PR #42.

**Evidencia estática:** `useOrderStatusChange.ts` anterior carecía de una marca de envío; `executeStatusChange` invocaba `orderApi.updateStatus` directamente. `OrderDetailContent.vue` posee dos vías de invocación de esta función; `orderApi.updateStatus` hace PUT. No hay métricas de frecuencia real de doble clic.

## 3. Corrección en rama

- `src/composables/useOrderStatusChange.ts`: se mantiene un `Set<number>` local con los IDs en vuelo. La marca se agrega **antes** de llamar a la API, se consulta tanto desde la vía de clic como desde la función usada por el modal, y se libera en `finally` ante éxito o error.
- `src/composables/__tests__/useOrderStatusChange.singleflight.test.ts`: cuatro casos nuevos con APIs simuladas: doble clic sobre mismo ID (una llamada y un callback), invocación directa repetida desde modal, IDs diferentes no bloqueados, reintento después de error.
- La cola **no reprograma automáticamente** una segunda transición: su propósito es descartar eventos repetidos mientras la operación anterior no ha terminado. La pantalla muestra mensaje de éxito/error de la operación original.
- No cambia precios, pagos, reglas de transición, descuentos, stock, roles, headers de concurrencia, estado fiscal, RLS ni SQL.
- No se introduce caché global ni cambio de API. El guard es local a la instancia del componente, para no introducir bloqueos entre sesiones/sucursales.
