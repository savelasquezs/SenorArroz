## 1. Flujo, causa raíz y alcance

1. `src/components/layout/EmployeeLeaveNavigation.vue`, `src/views/EmployeeLeavesView.vue` y `src/views/EmployeeLeaveDetailView.vue` realizan lecturas en `onMounted`: resumen por `employeeLeavesStore.refreshSummary()`, listado/detalle/historial según vista.
2. Las tres instancian `src/composables/useEmployeeLeaveUpdates.ts`, que se suscribe a `EmployeeLeaveChanged` mediante `useSignalR(ORDERS_SIGNALR_HUB_URL)`. El código base observaba `connectionState` y llamaba a `refresh()` **en toda transición a connected, incluida la primera**. Una lectura inicial terminada antes de conectar podía dispararse de nuevo. `src/store/employeeLeaves.ts` coalescea únicamente solicitudes de resumen simultáneas **en vuelo**: por ello hay dos activadores, pero **no siempre dos peticiones HTTP efectivas**.
3. Lectura del resumen: `src/services/MainAPI/employeeLeaveApi.ts` → `GET /api/employee-leaves/summary` → `SenorArroz.API/Controllers/EmployeeLeavesController.cs` (autenticado) → `SenorArroz.Application/Features/EmployeeLeaves/EmployeeLeaveQueries.cs` → EF Core (`Users`, `EmployeeLeaveRequests`, consulta de actor y conteos de no leídos/pendientes si corresponde). El scope sigue siendo del usuario autenticado; no se introduce ni cambia autorización.
4. La notificación sale del controlador a grupos de usuario `EmployeeLeaveRealtime.UserGroup`. `OrderHub.OnConnectedAsync` une conexiones autenticadas elegibles a dicho grupo. `src/composables/useSignalR.ts` mantiene conexiones compartidas y handlers por instancia; no se modifica. Los demás eventos de pedidos no se tocan.
5. No se modifica Flutter (`delivery_app`), Next.js (`senor-arroz-web-nextjs`), agente Windows (`senorArrozPrintAgent`), workers, endpoints, grupos de tenant ni datos. Se consultaron los PR abiertos: API #53 es de Rappi y no solapa; sin PR abiertos en frontend, Flutter, Next.js o Print Agent antes de esta corrección.

**Hallazgo comprobado:** doble *activador* de refresh de permisos al inicio (montaje + conexión normal), con posible petición posterior. **No demostrado:** cantidad real de HTTP repetidos, peso del payload, latencia, ahorro de consultas o coste de infraestructura en producción.

## 3. Corrección y regresiones

- **`src/composables/useEmployeeLeaveUpdates.ts`:** omitir el primer `connecting → connected` exitoso, porque las pantallas ya cargan inicialmente. Mantener `refresh()` en reconexiones y, de forma específica, al recuperarse de un error inicial; sin perder la lectura tras volver la pestaña visible o recibir `EmployeeLeaveChanged`. Permanecen `on/off` y los listeners del documento con su cleanup.
- **`src/composables/__tests__/useEmployeeLeaveUpdates.test.ts`:** seis pruebas con estados simulados: primera conexión sin refetch, reconexión verdadera, error de arranque recuperado, montaje sobre conexión ya establecida, evento/visibilidad y desmontaje sin listeners.
- No se añaden dependencias, cachés globales ni reintentos nuevos. La corrección no altera datos financieros, rutas, inventario ni tokens.
