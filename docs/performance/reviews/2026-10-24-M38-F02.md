## 1. Diagnóstico y corrección de la hipótesis inicial

Flujo: `EmployeeLeaveNavigation` / `EmployeeLeavesView` / `EmployeeLeaveDetailView` → `useEmployeeLeaveUpdates` / store / API cliente → `GET /api/employee-leaves` y resumen/detalle/historial → `EmployeeLeavesController` → `EmployeeLeaveQueries` → EF/PostgreSQL. El servidor emite `EmployeeLeaveChanged` con `publicId` y `version` al grupo autorizado de cada usuario mediante `OrderHub`.

La auditoría inicial encontró dos activadores: montaje y conexión SignalR. El primer commit `9d7e254` omitía siempre la primera conexión normal. La revisión posterior demostró que **no era seguro generalizar esa omisión**: un cambio producido después del snapshot HTTP y antes de la suscripción podía quedar sin recoger. Por tanto, el resultado final reemplaza ese enfoque y conserva la resincronización necesaria; no promete eliminar toda consulta al conectar.

También se confirmó que el payload del evento se descartaba; un cambio ajeno podía recargar el detalle o marcar un formulario abierto como conflictivo. Las vistas podían iniciar varias lecturas después de compartir un mismo resumen. La deduplicación anterior del resumen no conservaba una lectura posterior ante cambios ocurridos mientras consultaba. Las continuaciones de detalle/historial podían seguir trabajando después de una navegación.

La revisión final detectó además un contador desactualizado si el POST de marcado de leído terminaba mientras otra resincronización sustituía la lectura en curso; se corrigió y se añadieron pruebas específicas antes de fusionar.

### Garantías y límites del diseño

Las señales coincidentes antes de comenzar una lectura se agrupan. Si la conexión se establece después de comenzar o completar la consulta inicial, se hace una lectura posterior para cerrar la ventana. Durante una ráfaga se conserva el estado más reciente sin multiplicar lecturas concurrentes del mismo recurso. El catálogo y los contadores no se reutilizan entre identidades.

Una reconexión o el regreso a la pestaña no son prueba de un conflicto: con una operación abierta se compara la versión y se conserva el borrador. Un evento de otra solicitud no recarga ni bloquea el detalle, pero sí puede actualizar el resumen global. Los controles de versión y contraseña del backend permanecen como autoridad final.

## 4. Evidencia de comportamiento e impacto

| Escenario controlado | Resultado comprobado |
|---|---|
| Navegación y listado montados juntos | Comparten la solicitud inicial de resumen. |
| Conexión completa antes de iniciar la lectura | Se agrupan los activadores en una carga. |
| HTTP anterior a la conexión o conexión durante HTTP | Resincronización posterior: no queda el snapshot antiguo. |
| Ráfaga durante una lectura | Una lectura en curso y una posterior para recoger cambios; no lecturas paralelas por cada aviso. |
| Evento de otra solicitud o versión conocida | No recarga/bloquea el detalle abierto. |
| Visibilidad con formulario sin cambio de versión | Conserva el borrador sin falso conflicto. |
| Cambio de ruta/sesión o desmontaje | Aborta y descarta la respuesta; no inicia historial o marcado de leído posterior. |
| Marcado de leído solapado con resincronización | El contador se refresca después del éxito de la escritura mientras siga en el mismo contexto. |

Estos resultados son aserciones de pruebas con transporte controlado, no mediciones de tráfico productivo. HTTP/SQL real, latencias p50/p95, CPU/RAM, bytes, egress y EXPLAIN permanecen **sin medir**. No se infiere un porcentaje de ahorro ni se añaden índices especulativos.
