`src/views/BranchesList.vue` → `src/store/branches.ts` → `branchApi.getBranches` → `GET /api/Branches` → `BranchesController.GetBranches` → `GetBranchesHandler` → `BranchRepository.GetPagedAsync` y cinco métodos `CountAsync` por sucursal → tablas de usuarios, clientes y barrios mediante EF/PostgreSQL.

El bucle del [handler original](https://github.com/savelasquezs/SenorArroz/blob/925db805526a91a73722f660455d19e33c30ae6e/SenorArroz.Application/Features/Branches/Queries/GetBranchesHandler.cs) ejecutaba `GetTotalUsersAsync`, `GetActiveUsersAsync`, `GetTotalCustomersAsync`, `GetActiveCustomersAsync` y `GetTotalNeighborhoodsAsync` para cada fila. Para N sucursales eran 5N consultas de estadísticas, adicionales a la paginación. [Repositorio original](https://github.com/savelasquezs/SenorArroz/blob/925db805526a91a73722f660455d19e33c30ae6e/SenorArroz.Infrastructure/Repositories/BranchRepository.cs).

No se halló necesidad de cambiar SignalR, Flutter, Next.js, Print Agent ni workers para corregir ese bucle. No se introduce caché: los totales continúan consultándose en cada petición del listado. Permisos de endpoints y filtros tenant existentes permanecen intactos.

## 3. Corrección implementada en rama

| Archivo | Cambio |
|---|---|
| `SenorArroz.Application/Features/Branches/Queries/GetBranchesHandler.cs` | Una llamada batch con los IDs de la página; propaga cancelación a paginación y estadísticas; conserva DTO y metadatos. |
| `SenorArroz.Domain/Interfaces/Repositories/IBranchRepository.cs` | Contrato batch y record inmutable `BranchListStatistics` para los cinco contadores. |
| `SenorArroz.Infrastructure/Repositories/BranchRepository.cs` | Tres agregaciones agrupadas por sucursal, sin consultas por fila. |
| `SenorArroz.Tests/BranchListBatchStatisticsTests.cs` | Cinco casos ejecutables, incluidos dos casos parametrizados del handler y uno PostgreSQL. |

Usuarios y clientes calculan total/activos en una agregación por tabla. Barrios conserva el total, incluidos inactivos, tal como hacía el código previo. Los IDs se deduplican, las filas sin datos producen ceros y la lista vacía no dispara SQL. No se cargan colecciones completas. Las tres consultas se esperan secuencialmente sobre el mismo DbContext; no se añade `Task.WhenAll` ni un caché de resultados.

Se mantienen filtros globales de tenant y RLS existentes, sin `IgnoreQueryFilters`, consultas SQL manuales ni ampliación de permisos. La entrada del handler solo contiene IDs de las sucursales ya paginadas. La cancelación se propaga del handler al repositorio; no se modificaron los controladores.
