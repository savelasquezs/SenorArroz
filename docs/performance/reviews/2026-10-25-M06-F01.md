## 1. Causa raíz y ampliación aprobada

La corrección original invalidaba respuestas de búsquedas anteriores, pero no cancelaba su transporte. La UI también confundía una lista temporalmente vacía durante debounce/HTTP con ausencia de clientes y ofrecía crear uno prematuramente. Además, observar únicamente la prop `branchId` no cubría al POS: CustomerSection no la pasa porque la sucursal de búsqueda/sesión y la sucursal de atención de la dirección son distintas.

El selector utilizaba el listado completo, con hasta 100 clientes, direcciones y cobertura, destinatarios fiscales, estadísticas y fidelización antes de conocer qué cliente elegiría el operador. El propietario aprobó incluir las mejoras de UI, contexto, cancelación y consulta ligera en los PR existentes.

Flujo nuevo: CustomerSelector → CustomerLookupApi → `GET /api/customers/lookup/search` → CustomerLookupController → MediatR → GetCustomerSuggestionsHandler en infraestructura → proyecciones EF/PostgreSQL. Al seleccionar: `GET /api/customers/lookup/{id}` → handler existente GetCustomerByIdHandler → DTO completo con direcciones, estadísticas y fidelización. Las mutaciones de clientes y los endpoints existentes se conservan.

## 2. Implementación

### Frontend

- `src/components/customers/CustomerSelector.vue`: estados idle/debounce/carga/éxito/error/selección; resultado vacío y creación solo tras búsqueda exitosa sin coincidencias. Entrada de un carácter no dispara consulta. Reintento explícito sin mostrar errores técnicos del transporte.
- Contexto efectivo: sucursal explícita cuando la suministra WhatsApp/Rappi; en otro caso selección de Superadmin o sucursal asignada al usuario. La sucursal operativa de entrega no se sustituye por la de búsqueda ni viceversa. Cambiar identidad/rol/sucursal invalida resultados y solicitudes.
- AbortController más generación/texto/scope: abortar HTTP obsoleto, descartar resultados tardíos aunque el transporte ignore abort, cancelar selección en curso al cambiar consulta/sesión o desmontar y no emitir un cliente incompleto.
- Resultados accesibles como botones, diez sugerencias por página y opción «Ver más coincidencias». Un fallo en la página siguiente conserva las coincidencias ya encontradas y permite reintentar.
- `src/services/MainAPI/customerLookupApi.ts`: cliente de lectura dedicado que reutiliza BaseApi y sus interceptores de autenticación/sucursal; no añade estado global a los listados administrativos. El store de clientes continúa gestionando la creación sin cambiar su contrato.
- La selección consulta y valida el cliente completo antes de emitir el evento existente, preservando direcciones y fidelización para pedidos nuevos o persistidos. Rechaza clientes inactivos.

### Backend

- `SenorArroz.Application/Features/Customer/Queries/GetCustomerSuggestionsQuery.cs`: contrato de consulta y DTO mínimo.
- `SenorArroz.Infrastructure/Repositories/GetCustomerSuggestionsHandler.cs`: proyección AsNoTracking, página de 10 más una fila para `hasMore`, orden estable y coincidencias exactas prioritarias. Una segunda consulta obtiene nombres de empresas solo para los clientes visibles. Sin COUNT global, colecciones de direcciones, estadísticas ni fidelización por sugerencia.
- `SenorArroz.Infrastructure/DependencyInjection.cs`: registra el read model PostgreSQL de forma scoped para MediatR; no se agrega una dependencia de proveedor a Application.
- `SenorArroz.API/Controllers/CustomerLookupController.cs`: endpoints autenticados y no-cache, validación de sucursal existente y propagación del CancellationToken de MVC a MediatR/EF. El detalle reutiliza la autorización y el aislamiento tenant del handler existente.
- Semántica conservada y probada frente al repositorio anterior: teléfono móvil exacto puede encontrar la identidad en otras sedes del mismo tenant; nombre, teléfono parcial, usuario y coincidencias fiscales permanecen en la sucursal autorizada. No se usa IgnoreQueryFilters ni se modifican RLS o permisos.

No cambia SignalR, Flutter, Next.js, Print Agent, datos financieros, políticas de creación, dependencias ni workflows. No se añaden índices sin planes y métricas que los justifiquen.

## 5. Compatibilidad, migración y reversión

**Migración BD: no aplica. SQL pendiente: ninguno.** No hay cambios de esquema, índices, entidades o datos; no se necesita backfill ni backup extraordinario para esta entrega. Se mantienen los backups operativos habituales.

Orden recomendado: revisar/validar ambos PR → integrar API #66 → integrar Vue #43 → comprobar la publicación automática y el funcionamiento real. No se realizan despliegues manuales ni operaciones contra PostgreSQL productivo como parte de esta revisión.

Para una ventana de publicación desigual o rollback de API, el cliente recurre al endpoint anterior **solo ante 404/405** del nuevo endpoint. No lo hace ante 401/403, error de servidor o cancelación. `/customers/lookup/search` evita que un servidor antiguo intente interpretar `lookup` como el ID entero de `/customers/{id}`. El fallback conserva páginas de diez, pero temporalmente vuelve a cargar datos completos y no garantiza cancelación hasta EF en el servidor antiguo; es compatibilidad, no la optimización final. No debe usarse para declarar mejoras antes de confirmar la nueva API publicada.

Reversión: crear una rama y PR que revierta primero el merge frontend; la API nueva es aditiva y puede permanecer o revertirse después. Si se revierte primero la API, el fallback mantiene el uso de los contratos anteriores. Confirmar el comportamiento en ambos órdenes; no revertir datos ni ejecutar SQL. Usar los SHA de merge reales registrados en los PR, no los commits de prueba.
