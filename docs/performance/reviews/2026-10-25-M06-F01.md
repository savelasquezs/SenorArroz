## 1. Selección, flujo y causa raíz

Al revisar los PR abiertos el 25-oct se comprobaron dos correcciones distintas en curso: M03-F03 (API #62 / docs #63) y M12-F01 (API #64 / Vue #42 / docs #65). El listado M10-F02 utiliza `OrdersList.vue`, que ya modifica Vue #42, por lo que para evitar superposición se seleccionó M06-F01, pendiente en el checklist y frecuente en POS.

Flujo: `CustomerSection.vue` → `CustomerSelector.vue` (entrada y pegado de teléfono, debounce 400 ms) → `useCustomersStore.searchCustomers` → `customerApi.getCustomers` → `GET /api/customers?search=...&branchId=...` → `CustomersController.GetCustomers` → `GetCustomersHandler` → `CustomerRepository.GetPagedAsync` → EF Core/PostgreSQL (Customers, Phones, Addresses, BranchServices, BillingRecipients); estadísticas y adelantos de fidelización se agregan desde el handler. `GetCustomerByPhone` es otra ruta del store y no se modifica.

El repositorio usa AsNoTracking/AsSplitQuery y filtra `TenantId`. Un número telefónico exacto normalizado puede buscarse en otras sucursales del mismo tenant como identidad única; las demás búsquedas conservan el filtro de sucursal. El cambio **no** modifica esta regla, permisos de controlador ni RLS.

Defectos comprobados por inspección del código anterior:
1. Para una búsqueda de longitud 1, `handleSearch` retornaba **antes** de `cancelPendingSearch()`; un temporizador o respuesta antigua podían seguir vivos.
2. La petición comprobaba `searchGeneration` antes del `await`, pero asignaba la respuesta a `searchResults` sin comprobar otra vez: una respuesta lenta podía sobrescribir la coincidencia más reciente.
3. Cambiar la prop `branchId` conservaba el resultado de la sucursal anterior hasta que el usuario editara el texto.

La recuperación de resultados de una petición antigua también podía dejar mensajes de error correspondientes a una búsqueda que el operador ya había sustituido. Son riesgos reproducibles con promesas de prueba; no existe una medición de cuántas veces ocurrieron con HTTP real.

Dependencias revisadas: el componente se usa desde POS y atención, mientras la API usa consultas EF. Ninguna operación necesita modificar `OrderHub`, SignalR, Flutter, el sitio Next.js, Print Agent, workers ni el checkout. No existe un PR abierto específico de M06-F01 en esos repositorios.
