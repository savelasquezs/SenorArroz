## 1. Flujo y causa raíz
`OrderSidebar.vue` / `useOrderItems.ts` → `useOrderBenefitResolver.resolveBenefits()` → `loadLoyaltyCycle(branchId)` → `loyaltyCycleApi.getCycle` → `GET /api/branches/{branchId}/loyalty-cycle` → `LoyaltyCycleStepsController.Get` → `IApplicationDbContext.LoyaltyCycleSteps` con `Include(GiftProduct.Category)`, `AsNoTracking`, filtro `BranchId`, orden por `StepIndex`, `ToListAsync(cancellationToken)` → EF Core/PostgreSQL (LoyaltyCycleSteps, productos y categorías relacionados).

Se confirma en código que `loadLoyaltyCycle()` primero consulta `cycleByBranch` y no vuelve a consultar una sucursal presente. El bloque `catch` antiguo escribía `cycleByBranch.set(branchId, [])` ante cualquier error HTTP. Una falla temporal de la API (o de red) era indistinguible de una respuesta válida con cero pasos y quedaba cacheada durante toda la vida del módulo. Cuando el cliente tenía recompensa pendiente, las siguientes resoluciones devolvían siempre el ciclo vacío; el frontend omitía el premio aunque se recuperase la API.

La consulta GET está protegida por `Authorize(Roles = "Superadmin,Admin,Cashier")`, `AllowCrossBranchOrderContext` y la comprobación de rol `CanReadBranch`; la consulta del backend usa el contexto de DB correspondiente. No se ha probado de forma independiente la seguridad RLS ni el plan SQL en esta auditoría. No hay SignalR involucrado en esta llamada de lectura; Flutter, Next.js y Print Agent no participan en este subflujo de consulta de fidelización del POS. El código del backend no requiere corrección.

**Comprobado:** caché de fallo indefinida; `cycleInFlight` ya deduplica llamadas simultáneas. **No comprobado:** frecuencia real de fallos de la API, p50/p95, N+1 SQL en producción, índice óptimo, tráfico y egress productivos. No se proponen índices ni caché adicional sin medición.

## 3. Corrección y pruebas
- `src/composables/useOrderBenefitResolver.ts`: eliminar exclusivamente `cycleByBranch.set(branchId, [])` del `catch`. Tras fallo sigue retornando `[]` a la resolución actual como antes, pero sin convertirlo en estado persistente. Una nueva resolución puede volver a solicitar el ciclo; éxitos y listas vacías legítimas siguen cacheados por rama.
- `src/composables/__tests__/useOrderBenefitResolver.lifecycle.test.ts`: regresión con un primer GET sintético rechazado, segundo exitoso con una recompensa activa y tercero servido desde caché, comprobando invocaciones y aplicación.
- No se alteran reglas para seleccionar un único beneficio, cuantías, descuentos, pagos, facturación, permisos, contratos HTTP, rutas, escrituras, sincronización SignalR ni otras aplicaciones.
- Se mantiene la deduplicación `cycleInFlight`. **Riesgo residual:** si falla la API reiteradamente, una nueva resolución reintenta en vez de usar un fallo cacheado. Es intencional para recuperar un beneficio; si se observan tasas elevadas de error, analizar backoff breve con telemetría. Otro riesgo anterior: respuestas exitosas cacheadas indefinidamente pueden quedar obsoletas hasta recargar; fuera del cambio mínimo.
- Prueba propuesta que fallaría antes y pasaría después: tras GET rechazado, segundo GET debe ocurrir y permitir aplicar la recompensa; tercer intento no debe hacer HTTP.
- **CI:** consultar [Frontend PR #67](https://github.com/savelasquezs/senorArrozFront/pull/67/checks) antes de marcar listo. Si no hay pruebas completadas, ambos PR deben permanecer en borrador.
- No hay mediciones productivas ni pruebas manuales en una caja.
