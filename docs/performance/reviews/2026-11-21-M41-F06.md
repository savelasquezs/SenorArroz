## 1. Selección, flujo y causa raíz

Se revisaron README, CHECKLIST, REVIEW_TEMPLATE, PR recientes [#153](https://github.com/savelasquezs/SenorArroz/pull/153) y [#154](https://github.com/savelasquezs/SenorArroz/pull/154), y la lista de PR abiertos: no había una corrección M41-F06 en curso. Los features M41-F01 a F05 tienen PR de corrección abiertos; se seleccionó exactamente M41-F06.

**Flujo representativo:** vista de mapa POS `DeliverymenManagementView.vue` → `GET /api/deliverymen/map` → `DeliverymanController` → `GetDeliveryMapQuery` y handler → consultas EF Core → `ApplicationDbContext` → comandos Npgsql/PostgreSQL. El mismo mecanismo de conexión es transversal a endpoints, workers y consultas de Vue, Flutter y Next.js. SignalR no es el origen del defecto: únicamente puede incrementar la frecuencia de lecturas que llegan a EF. El agente de impresión y otros workers utilizan el mismo registro de contexto o conexiones Npgsql controladas, pero esta mejora no modifica esos flujos.

**Defecto comprobado en código:** `SenorArroz.Infrastructure/Data/TenantDbSession.cs` implementa `TenantDbConnectionInterceptor.ConnectionClosing` y `ConnectionClosingAsync` ejecutando `ResetContextSql` con dos `set_config(...,false)` agrupados en un comando SQL **cada cierre**. Sin embargo, Npgsql reinicializa las conexiones reutilizadas con pooling normal; la aplicación ya valida en `ConnectionOpened` que `No Reset On Close` sea falso. Se paga el comando de limpieza adicional antes del restablecimiento normal del proveedor. Documentación técnica: [Npgsql — Pooled Connection Reset](https://www.npgsql.org/doc/performance.html#pooled-connection-reset) y [EF Core — Interceptors](https://learn.microsoft.com/en-us/ef/core/logging-events-diagnostics/interceptors).

**Seguridad:** `CurrentTenantService` resuelve el tenant por JWT o scope AsyncLocal; `TenantDbConnectionInterceptor.ConnectionOpened[Async]` aplica tenant/sistema al abrir y `TenantDbCommandInterceptor` lo actualiza antes de cada Reader, Scalar y NonQuery, incluso cuando cambia el scope durante la misma conexión. El test usa un rol restringido `NOBYPASSRLS`; no se desactivan RLS, permisos ni índices.

## 3. Corrección delimitada y prueba

- **Archivo funcional único:** eliminar `ResetContextSql`, métodos `Reset/ResetAsync` y ambos overrides `ConnectionClosing`; mantener intactos configuración de pooling, apertura de conexión y command interceptor. Con Npgsql pooling normal no se requiere ejecutar SQL adicional por cierre.
- **Prueba nueva:** `SenorArroz.Tests/MultitenantRlsPostgreSqlTests.cs`, con PostgreSQL aislado, rol restringido, `MaxPoolSize=1`, consultas SQL sin filtro EF en scopes sistema → tenant 1 → tenant 2, ocho lecturas alternadas concurrentes y lectura Npgsql externa que no debe heredar sesión. Complementa la suite existente para asegurar que el control del proveedor y los interceptores siguen aislando.
- **Pruebas / CI:** pendientes al registrar este informe. En GitHub Actions `Backend CI` se ejecutan pruebas .NET con PostgreSQL de servicio cuando esté habilitado; actualizar estado y descripción PR al comprobar resultados. No afirmar pruebas aprobadas todavía.
- **Riesgos:** cualquier desactivación futura de reset por `NoResetOnClose=true` sería incompatible y continúa explícitamente bloqueada; PgBouncer en modo transaction pooling requiere un diseño transaccional de tenant distinto, fuera de alcance. No afirmar mejora medida en producción.
