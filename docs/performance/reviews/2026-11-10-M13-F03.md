## 1. Flujo, evidencias y causa raíz
1. `src/views/KitchenView.vue` invoca el modal `ConfirmStatusChangeModal` cuando el operador marca uno o varios pedidos como `ready`. En modo cocina combinado, el helper `src/composables/kitchenMarkReadySequence.ts` ejecuta secuencialmente `taken → in_preparation → ready` para tomados, y solamente `ready` para pedidos en preparación.
2. `ConfirmStatusChangeModal.vue` tenía `isLoading` y un `BaseButton` deshabilitado por esa prop, pero `confirmAndUpdate` **no rechazaba una segunda invocación síncrona** antes de que Vue actualizase el DOM. Se podían disparar dos recorridos HTTP en paralelo desde un mismo modal. Además `BaseDialog` permite por defecto cerrar mediante Escape/backdrop, incluso mientras las mutaciones continúan; puede abrirse un nuevo modal mientras la primera secuencia sigue viva. Esto es defecto de coordinación local, no evidencia de frecuencia de duplicados productivos.
3. `src/store/ordersData.ts` → `orderApi.updateStatus` → **PUT `/api/orders/{id}/status`** → `SenorArroz.API/Controllers/OrdersController.cs` → `ChangeOrderStatusHandler.cs` → `IOrderRepository.ChangeStatusAsync` / EF Core sobre `Orders` y su contexto tenant/RLS. El handler verifica pertenencia y reglas de transición, abre transacción, lee detalles, escribe estado y audita; al pasar a `Ready` procesa notificación de domiciliarios, sincronización externa si aplica y encolado de impresión (notificaciones y agente vía SignalR después de almacenamiento). La transición previa a preparación puede consumir inventario. Repetir requests provoca trabajo de autenticación, transporte, consulta/validación y conflicto; **no está demostrado que produzca dos impresiones**, pues el servidor puede rechazar la segunda transición.
4. `BaseButton.vue` previene clics tras re-renderizado, pero no es garantía de exclusión mutua síncrona en la función. El control backend de transición y permisos sigue siendo autoridad; esta mejora evita trabajo redundante desde una instancia del modal.
5. Relacionados, **no duplicar:** [M13-F02 Vue #78](https://github.com/savelasquezs/senorArrozFront/pull/78) añade guard por ID en `KitchenView.executeStatusChange` para Tomado→Preparación; [M13-F04 Vue #72](https://github.com/savelasquezs/senorArrozFront/pull/72) trata reimpresión manual. Ambos permanecen separados. [M13-F01 informe anterior](2026-10-15-M13-F01.md) optimizó la carga y SignalR, no el diálogo.
6. Revisión de otros repos: `delivery_app` participa en estados/rutas posteriores, `senor-arroz-web-nextjs` en checkout, y `senorArrozPrintAgent` en recepción de impresión. Ninguno origina esta doble invocación del modal; no se justifican modificaciones allí.

**Hecho confirmado:** la función carecía de guard síncrono y el diálogo era descartable durante la mutación. **Hipótesis no probadas:** frecuencia de doble clic real, duplicados de impresión, saturación SQL o ahorros cuantificados.

## 3. Corrección mínima, seguridad y pruebas
**PR Vue #79:** `if (isLoading.value || !props.isOpen) return` toma la exclusión antes de cualquier `await`; `finally` libera en éxito/error. `requestClose` y `:dismissible="!isLoading"` impiden abandonar/reabrir inadvertidamente el diálogo durante la operación. Un error conserva el diálogo y permite reintentar. No se altera el número de solicitudes de **una** ejecución legítima, orden del lote, autorización, reservas, precios, dinero, inventario, impresión, notificaciones o estados permitidos.

**Regresiones añadidas** `src/components/kitchen/__tests__/ConfirmStatusChangeModal.performance.test.ts`: doble evento en el mismo tick solo inicia un PUT; la cadena `taken→in_preparation→ready` se ejecuta una vez; error libera exclusión y admite reintento; intentar cerrar durante request se ignora. Resultado CI se añadirá al PR tras ejecutarse. No se ejecutaron pruebas locales; GitHub Actions se usa para build, typecheck y Vitest.

**Riesgos:** protección local únicamente (no múltiples pestañas/dispositivos); usuarios no pueden cerrar el modal durante una petición lenta (comportamiento deliberado para evitar confusión); QA de lotes con fallo parcial y conectividad lenta; compatibilidad con Vue #72 y #78, cambio de sucursal y permisos. API mantiene tenant/RLS y validación. No crear caché, índices ni paralelizar lote sin evidencia.
