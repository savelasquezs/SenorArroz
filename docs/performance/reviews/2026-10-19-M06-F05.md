## 1. Flujo y causa raíz

`CustomersList.vue` y `CustomerSelector.vue` → `src/store/customers.ts` → `customerApi.getCustomers` → `GET /customers` → `CustomersController` → `GetCustomersHandler` → `CustomerRepository.GetPagedAsync` / `LoyaltyCycleService` → `Order` / `LoyaltyCycleStep` (EF Core/PostgreSQL).

**Problema confirmado en código:** por cada cliente de una página se consultaban individualmente conteo de pedidos válidos, fechas primera/última y suma de totales (**3N agregaciones** para N clientes). El preview de fidelización realizaba además entre 2N y 3N consultas a conteos y configuración por cliente. Los handlers de detalle por ID/teléfono y edición repetían tres agregaciones.

El listado incluye `Phones`, `Addresses` y `BranchServices`, múltiples colecciones susceptibles de multiplicación de filas mediante JOIN. La ordenación carecía de desempate único. No hay evidencia de solicitudes HTTP duplicadas, causas SignalR ni participación de Flutter, Next.js o agente de impresión en este flujo.

**Verificación frontend:** `CustomersList.vue` usa el número de direcciones y la selección para pedidos requiere los datos del cliente/direcciones. Una proyección que eliminara esas relaciones rompería consumidores o requeriría llamadas extra. Por eso se conserva el JSON y no se modifica Vue.

## 2. Corrección en rama

- `CustomerRepository.GetOrderStatisticsForCustomersAsync`: agrupa en una consulta por IDs de clientes y tenant; filtra `Cancelled` y `AwaitingPayment`, y devuelve conteo, fechas, suma y entregados. Página vacía no consulta pedidos.
- `CustomerOrderStatisticsExtensions`: proyecta estadísticas cero/null de manera uniforme. Reutilizada en listado, detalle, búsqueda por teléfono y actualización.
- `LoyaltyCycleService.ApplyLoyaltyPreviewsToCustomerDtosAsync`: aprovecha `LoyaltyDeliveredCount` del agregado, consulta pasos activos para todas las sucursales de la página y calcula premios en memoria, compartiendo lógica con el preview individual. No cambia `OnOrderDelivered` ni `OnOrderLeftDelivered`.
- `LoyaltyCycleStepRepository.GetActiveStepsForBranchesAsync`: lectura acotada por sucursales con filtros globales de tenant y solo pasos activos. Sin caché persistente ni estado cruzado entre tenants.
- `GetPagedAsync` y `GetByIdWithAddressesAsync`: `AsSplitQuery()` para evitar producto cartesiano de colecciones. `ThenBy(c => c.Id)` ofrece páginas deterministas incluso con nombres/teléfonos/fechas iguales.
- Se retiran `GetOrderDateRangeAsync` y `GetTotalOrderRevenueAsync`, ya sin consumidores. Se mantiene `GetTotalOrdersAsync` porque `CustomerBusinessRules` todavía lo utiliza.
- No se agregan índices sin evidencia `EXPLAIN`; no se cachean datos de pedidos/fidelización.

## 3. Línea base y comparación

| Indicador | Antes | Después | Naturaleza de evidencia |
|---|---|---|---|
| SQL estadísticas, lista N>0 | 3N agregaciones individuales | 1 agregación agrupada | Derivado del código; **no medido** |
| SQL fidelización, lista N>0 | N conteos + N ciclos + hasta N premios | 1 consulta de pasos; entregados dentro del agregado | Derivado del código; **no medido** |
| Estadísticas en detalle/teléfono/edición | 3 lecturas individuales | 1 agregación + 1 lectura de pasos para preview | Derivado del código; **no medido** |
| Relaciones de cliente | Varias colecciones en joins | Split query con más viajes SQL pero sin combinatoria de filas | Efecto técnico; **sin benchmark** |
| Solicitudes HTTP, SQL total, p50/p95, EXPLAIN, bytes/egress, RAM/CPU, errores | Sin medir | Sin medir | Sin acceso/ejecución de perfil productivo |

**No se inventan métricas de mejora**; no hay medición comparativa de tiempo total, memoria ni egress. Split queries pueden aumentar viajes SQL y producir lecturas no atómicas de relaciones bajo concurrencia.
