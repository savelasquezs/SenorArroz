## 1. Flujo y diagnóstico

`WhatsAppController.UpdateOperationalBranch` valida rol/acceso, persiste la reasignación con EF Core/PostgreSQL y publica `WhatsAppConversationRoutingChanged` mediante `WhatsAppNotificationService` a grupos tenant/sucursal/usuario del `WhatsAppHub`. La vista consulta `GET /api/whatsapp/conversations` y `GET /api/whatsapp/unread-summary`; el primero incluye sucursales/cliente y obtiene nombres de asesores y motivos IA, mientras el segundo agrega no leídos. El store ya comparte solicitudes simultáneas idénticas.

La auditoría original incorporó una cola solamente para eventos de reasignación y su acción manual. La revisión posterior encontró que montaje, búsqueda, filtros, botón Actualizar y polling seguían fuera de esa cola. Un evento podía reutilizar una lectura iniciada antes del cambio, sin garantizar otra posterior. Asimismo, `Promise.all` podía terminar por un error del contador mientras el listado seguía pendiente, haciendo que la siguiente recarga reutilizara esa lectura antigua.

La respuesta de una transferencia podía reemplazar la conversación seleccionada aunque el operador hubiera abierto otro chat. Una reasignación remota tampoco invalidaba el contexto del pedido del mismo ID en otra sucursal. La reconexión detenía el polling sin resincronizar la bandeja. Finalmente, un fallo del GET posterior a un PUT confirmado se presentaba como si la transferencia hubiera fallado. Son defectos de coordinación demostrados con pruebas controladas, no incidentes productivos medidos.

## 2. Corrección localizada

| Archivo | Cambio |
|---|---|
| `src/views/WhatsAppView.vue` | Unifica las entradas de recarga; espera ambas lecturas, protege selección/sesión/desmontaje, renueva contexto al cambiar sede, resincroniza al reconectar y diferencia fallos de escritura y lectura. |
| `src/store/whatsapp.ts` | Recibe cancelación opcional en listado; no reutiliza peticiones abortadas; limpieza por identidad de solicitud; ignora respuesta de transferencia de otra sesión. |
| `src/utils/whatsappRoutingRefresh.ts` | Reutiliza `createSerialRefresh`, transmite contexto de vigencia/cancelación y sustituye la cola al cambiar filtros. |
| `src/views/__tests__/WhatsAppView.routing.test.ts` | 16 regresiones con vista, store Pinia y cola reales; transporte HTTP/SignalR simulado. |
| `src/utils/__tests__/whatsappRoutingRefresh.test.ts` | 6 pruebas de la cola, incluidas tres nuevas de cancelación/cambio de contexto. |

Se conserva la cola común existente, sin modificar `serialRefresh.ts` ni `useSignalR.ts`. No se añade caché global, bibliotecas, contratos HTTP o SQL. No se alteran permisos, reglas de asignación, precios, pagos, grupos SignalR o políticas RLS.

### Comportamiento

- Todas las llamadas de la vista a `reloadConversations` pasan por la misma coordinación. Eventos recibidos durante una lectura conservan una lectura posterior; varias señales antes de comenzar se agrupan.
- Las dos lecturas terminan mediante `Promise.allSettled` antes de procesar la siguiente invalidación. Un fallo de no leídos no obliga a descartar un listado correcto; el usuario ve un aviso con reintento.
- Cambiar filtros cancela el listado inmediatamente, respetando el debounce existente. Una consulta nueva puede empezar sin esperar que el transporte antiguo responda; sus respuestas obsoletas se descartan, incluso en A → B → A. El contador global sigue compartido con otros consumidores, por lo que no se cancela indiscriminadamente.
- La transferencia se bloquea desde antes del diálogo, para evitar dos confirmaciones superpuestas. Se captura selección/sesión y se comprueba después de cada espera relevante. No se vuelve al chat anterior ni se inicia una recarga tras abandonar la vista.
- El cambio real de sucursal del chat abierto renueva el contexto y descarta el borrador de la sucursal anterior. Eventos de otros chats no provocan esa carga. Se contemplan respuestas locales que mutan el objeto del store y eventos remotos.
- Una reasignación confirmada no se revierte visualmente por un fallo de la lectura posterior; se comunica que el cambio se guardó y que la bandeja necesita reintento.
- Una respuesta del cliente con `addresses: []` es válida: no se vuelve a consultar direcciones en la carga de contexto o vinculación. Se mantiene el respaldo cuando la propiedad está omitida o no es un array.

## 4. Impacto comprobable y lo no medido

| Caso | Evidencia disponible |
|---|---|
| Ráfaga en un mismo tick | Una invocación de lectura coordinada. |
| Evento durante listado inicial o refresco manual | Lectura posterior real en la prueba vista/store; no solo repetición del callback. |
| Falla temprana de no leídos con listado pendiente | No inicia la siguiente iteración hasta que ambos terminan; se obtiene la versión nueva. |
| Nuevo filtro mientras HTTP antiguo sigue pendiente | Se aborta el transporte anterior y la respuesta tardía no reemplaza el filtro vigente. |
| Cliente sin direcciones | Se evita la consulta adicional cuando el DTO contiene un array vacío válido. |
| CPU/RAM, SQL, egress, p50/p95, frecuencia de eventos y EXPLAIN | Sin medir. No se declara un porcentaje de ahorro. |

El store ya compartía determinadas peticiones; agrupar callbacks no equivale por sí solo a una reducción adicional de HTTP. La lectura posterior es intencional para conservar consistencia. La cancelación del navegador tampoco garantiza que una consulta ya terminada en el servidor haya consumido menos recursos.
